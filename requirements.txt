# PAAS_ensemble_v4 -- pinned requirements for the ONE venv used by BOTH training and inference.
#
#   /datasets/work/vLLM/temp/PAAS_qwen3vl/venv/bin/python      (Python 3.12.12, CUDA 13.0)
#
# Every stage runs on this interpreter: Qwen3.5-4B LoRA/distill/merge, the functional gate, MIDS
# answer generation, all four detector trainers (MIDS-4c, A2_9c, GSD, SeLop), deployment, threshold
# calibration and the FastAPI server. train/_bootstrap.py and paas/env.py refuse to run on anything
# with transformers<5, because the tf5 CLIP ports (flattened .vision_model, tensor-returning
# CLIPEncoderLayer) and the in-process vLLM both require it.
#
# Versions are the exact set this pipeline was validated against -- pinned, not ranged, because
# several defects in this project came from silent API drift (e.g. albumentations 2.x renaming
# quality_lower/upper, which disabled JPEG augmentation without an error).
#
# ISOLATION (2026-08-14): the venv is now SELF-CONTAINED and must stay that way.
#   pyvenv.cfg          include-system-site-packages = false   (backup: pyvenv.cfg.bak)
#   run_finetuning.sh   export PYTHONNOUSERSITE=1
#   guards              train/_bootstrap.py + paas/env.py abort if either is undone
# This is not cosmetic. ~/.local still holds a COMPLETE legacy stack -- transformers 4.37.2,
# peft 0.7.1, tokenizers 0.15.2, accelerate 0.21.0 -- which used to be inert only because the venv
# sorted earlier on sys.path. Any perturbation of that order would silently load tf4 and train a
# head that cannot be served. Verify at any time with:
#   venv/bin/python train/check_venv_isolation.py       # path + 28 modules + 6 deep imports + pins
#
# INSTALL ORDER MATTERS -- and three groups CANNOT be installed by plain resolution (see below):
#
#   python -m venv venv && . venv/bin/activate && pip install -U pip setuptools wheel
#   pip install torch==2.11.0 torchvision==0.26.0 torchaudio==2.11.0 \
#       --index-url https://download.pytorch.org/whl/cu130          # pulls numpy 2.x -- fixed below
#   pip install --no-deps opencv-python-headless==4.13.0.92         # (1)
#   pip install -c constraints -r requirements.txt                  # constraints = numpy + ml-dtypes
#   pip install --no-deps albumentations==2.0.8 albucore==0.0.24    # (2)
#   pip install --no-deps vllm==0.21.0 mistral_common==1.11.2 ...   # (3) + its chain
#
# Why --no-deps is REQUIRED in those three places (all trace to one root cause):
#  (1) opencv-python-headless 4.13.0.92 DECLARES numpy>=2, but this pipeline is validated on
#      numpy 1.26.4. The pair is ABI-fine (a C extension built against numpy 2 headers runs on
#      numpy>=1.19); pip treats the declaration as hard and returns ResolutionImpossible.
#  (2) albumentations REQUIRES opencv, which drags opencv's numpy>=2 declaration back into the
#      resolution -- same wall, one level up.
#  (3) vllm's closure cannot be resolved at all: mistral-common backtracks to no solution. Its
#      chain is therefore pinned to the exact versions the validated environment runs.
# Installing torch from plain PyPI first pulls a different CUDA build and vLLM then mismatches it.
